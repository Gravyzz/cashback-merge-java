# Проект 2. Cashback Merge

Мини-игра в духе 2048 на квадратном поле (`4x4` в примере кампании). На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.

Но у проекта есть второй, продуктовый слой. По итоговой плитке начисляется
награда, и эта награда стоит компании денег. Поэтому максимальную награду
должна получать ограниченная доля игроков — например, не больше `20%`.
Проверяется это симуляцией на тысячах «игроков» до запуска акции.

Задание разбито на три merge request'а. Делай их по очереди.

## Быстрый старт

```bash
./gradlew run     # вывести начальное поле и результат одного хода UP
./gradlew check   # запустить тесты и линтеры — ровно то, что проверяет CI
```

Нужен **JDK 25 или новее**. Gradle ставить не нужно — в проекте лежит `gradlew`,
он скачает нужную версию сам.

Сейчас приложение загружает `config/campaign.example.json`, создаёт игру
с `seed = 42` и выполняет один ход `UP`. Затем выводит изменённое поле,
очки за ход, общий счёт и оставшиеся ходы. Это демонстрация движка, а не
интерактивная игра: ввод команд пока не реализован. Одинаковые конфиг, seed
и последовательность ходов дают воспроизводимый результат.

Пример вывода:

```text
. . . .
. . . .
. . . 1%
. . . 1%
После хода UP:
. . . 2%
. . 1% .
. . . .
. . . .
true - изменилось ли поле
2 - очки за ход
Общий счет - 2
Оставшиеся ходы: 99
```

Точка `.` обозначает пустую клетку.

## Что реализовано в MR1

- квадратное игровое поле с размером из конфига (`4x4` в примере), проверкой координат и занятости клеток;
- состояние партии и учёт лимита ходов;
- конфигурация кампании с проверкой размера поля, лимита ходов и spawn-правил;
- загрузка конфигурации из JSON через Jackson;
- точные вероятности на основе `BigDecimal`;
- появление плиток в случайных свободных клетках согласно spawn-правилам;
- воспроизводимое начальное состояние по `seed`;
- текстовое представление игрового поля;
- модульные и обязательные тесты MR1.

## Что реализовано в MR2

- сдвиг и слияние плиток во всех четырёх направлениях;
- отдельный алгоритм обработки одной линии без изменения исходного массива;
- каждая плитка участвует не более чем в одном слиянии за ход;
- очки за ход равны сумме значений созданных при слиянии плиток и добавляются к общему счёту;
- ход учитывается только при изменении поля; после него появляется ровно одна новая плитка;
- ход без изменения поля не тратит лимит, не приносит очков и не создаёт плитку;
- после исчерпания лимита дальнейшие ходы отклоняются; получение плитки `32%` само по себе игру не завершает;
- `Game` связывает состояние партии с движком, а фабрика создаёт готовую к ходам игру;
- обязательные тесты MR2 и дополнительные проверки состояния, результатов и связи компонентов.

Размер поля из конфига используется и при обработке ходов. Один `TileSpawner`
с одним генератором `Random` обслуживает начальные плитки и последующие ходы.
Награды и массовая симуляция будут реализованы в MR3.

Значения плиток и счёт хранятся в `int`. Для примерной кампании этого достаточно;
защита от переполнения при очень больших значениях в произвольном конфиге пока
не реализована.

## Конфигурация кампании

Пример находится в `config/campaign.example.json`. Игровой движок использует поля:

```json
{
  "boardSize": 4,
  "movesLimit": 100,
  "spawnRules": [
    { "cashback": "1", "probability": "0.85" },
    { "cashback": "2", "probability": "0.15" }
  ]
}
```

Ограничения конфигурации:

- размер стороны поля `boardSize` должен быть не меньше `2`;
- лимит ходов должен быть положительным;
- список spawn-правил не должен быть пустым;
- кешбэк каждой плитки должен быть положительным;
- уровни кешбэка в spawn-правилах не должны повторяться;
- каждая вероятность должна быть больше `0` и не больше `1`;
- сумма вероятностей должна быть в точности равна `1`.

Кешбэк и вероятности в JSON записаны строками, чтобы при чтении не потерять
точность из-за типа `double`.

Реализован бонус: размер поля через конфиг. Например, `boardSize: 5` создаёт
поле `5x5`. Начальная партия всегда содержит две плитки; поэтому минимальный
размер стороны — `2`. Поля разных размеров могут существовать одновременно.

Пустой файл, некорректный JSON и неверные числовые строки отклоняются с
понятными сообщениями. Для ошибок числовых строк указывается поле и индекс
spawn-правила, исходное исключение сохраняется как причина.

## Структура игрового движка

| Компонент | Ответственность |
|---|---|
| `CampaignConfig`, `SpawnRule` | Хранят и проверяют настройки кампании |
| `ConfigLoader` | Читает JSON и создаёт валидный конфиг |
| `Board`, `Board.Position` | Представляют поле и неизменяемые позиции его клеток; позиции создаются через поле с полной проверкой границ |
| `GameState` | Хранит поле, общий счёт и использованные ходы |
| `TileSpawner` | Выбирает свободную клетку и значение новой плитки |
| `Direction` | Задаёт направление хода |
| `LineMerger`, `LineMergeResult` | Обрабатывают одну линию и возвращают новые клетки и прирост очков; результат защищает массив копированием |
| `MoveEngine`, `MoveResult` | Обрабатывают один ход всего поля, обновляют состояние и создают плитку только при изменении поля; возвращают признак изменения и очки за ход |
| `Game` | Связывает состояние партии и движок; позволяет выполнить ход без отдельной передачи состояния |
| `GameFactory` | Создаёт игру с двумя начальными плитками и общим для всей партии генератором случайных чисел |
| `BoardRenderer` | Преобразует поле в текст |
| `Main` | Демонстрирует начальное поле и один ход `UP` |

## Проверка

Полная локальная проверка:

```bash
./gradlew check
```

Тесты MR1 проверяют валидацию конфигурации, модель поля, состояние партии,
появление плиток, воспроизводимость по seed и точный формат текстового вывода.
Тесты MR2 проверяют правила слияния, направления ходов, начисление очков,
появление плитки, учёт лимита, отсутствие изменений при невалидном ходе,
защитное копирование массивов и связь созданной фабрикой игры с её состоянием.
Обязательные тесты MR2 включены; заготовки MR3 остаются с `@Disabled`, пока
соответствующая функциональность не реализована.
